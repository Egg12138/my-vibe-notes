#01 QOM 的设计动机与核心思想

1.1 C 语言的 OOP 困境

QEMU 是一个用 C 语言编写的全系统模拟器，需要建模数百种不同的硬件设备： PCI 网卡、USB 控制器、I2C 从设备、块设备……这些设备共享大量公共行为但又各有差异。 在 C 语言中，如何优雅地表达这种 "相似但不同" 的关系？

C 语言没有 class、inheritance、virtual function 这些原语，但 QEMU 开发者需要：

  • 类型继承 —— PCIDevice 是一个 Device，Device 是一个 Object
  • 虚函数表 —— 不同的 Device 有各自的 realize/unrealize/reset 实现
  • 自省 (introspection) —— 运行时查询设备有哪些属性，动态设置属性值
  • 动态类型注册 —— 编译型语言却需要插件式的类型发现
  • 引用计数 —— 对象间的生命周期管理
核心问题：C 语言中如何模拟面向对象？答案是 convention + macros + a central type registry。 QOM 正是在这个约束下设计出来的方案。

1.2 QEMU 1.x 的 "前 QOM" 时代

在 QOM 出现之前 (QEMU < 1.0)，设备通过 DeviceInfo 结构体静态定义： 

/* 旧式设备定义 —— 静态数组，没有继承，没有属性自省 */
static DeviceInfo e1000_info = {
    .name      = "e1000",
    .bus_type  = BUS_TYPE_PCI,
    .init      = e1000_init,     /* 唯一的"构造"回调 */
    .mmio_size = E1000_MMIO_SIZE,
};
static void e1000_register(void) {
    pci_qdev_register(&e1000_info);  /* 手动注册 */
}

这种模型有严重局限：

  • 没有继承 —— DeviceInfo 是扁平的，PCI 设备的公共代码只能靠 copy-paste
  • 没有类型链 —— 无法表达 "e1000 是一类 PCI 设备, PCI 设备是一类设备"
  • 没有属性自省 —— 无法通过 QMP 查询设备的属性列表
  • 静态注册 —— 类型必须在编译时就确定，无法通过 module 动态加载

1.3 QOM 的设计目标

QOM (QEMU Object Model) 于 2011 年引入，设计目标非常明确：

目标实现手段
类型层次结构TypeInfo → TypeImpl 的 parent 链
C 风格的 "vtable"ObjectClass 中的函数指针 + 父类 memcpy 继承
对象实例Object 结构 + 引用计数 + parent 链接 (composition tree)
属性自省ObjectProperty + Visitor pattern
动态类型加载type_init 宏 + module_load_qom() + CONFIG_MODULES
接口 (interface)InterfaceInfo + type_is_ancestor() 运行时检查
构造安全instance_init 不可失败 → realize 可以失败的两阶段构造

1.4 QOM 三层抽象

QOM 将 "类型" 的概念拆成三个层次：

Type (TypeImpl) ┌─────────────────────────────────────────────┐ │ name, parent │ │ class_size, instance_size, instance_align │ │ class_init, class_base_init │ │ instance_init, instance_post_init │ │ instance_finalize │ │ interface_info[] │ │ abstract (bool) │ └──────────────┬──────────────────────────────┘ │ 1:1 (singleton per type) ▼ Class (ObjectClass) ┌─────────────────────────────────────────────┐ │ type → (back pointer to Type) │ │ interfaces → GSList of InterfaceClass │ │ unparent → callback │ │ properties → GHashTable of ObjectProperty │ │ + │ │ vfunc ptrs (e.g. DeviceClass: realize, reset) │ └──────────────┬──────────────────────────────┘ │ 1:N (many objects per class) ▼ Instance (Object) ┌─────────────────────────────────────────────┐ │ class → (pointer to ObjectClass) │ │ free → destructor │ │ properties → child properties │ │ ref → reference count │ │ parent → parent Object in composition tree │ │ + │ │ instance data (DeviceState: id, realized...) │ └─────────────────────────────────────────────┘

这个三层架构是理解 QOM 的 核心心法：

  • Type 是类型的 元数据模板，全局只有一份，告诉 QOM "这个类型叫什么名字、父类型是谁、类型/实例分别多大、初始化回调是什么"
  • Class 是类型的 虚函数表，每个类型一份，由父类的 Class memcpy 而来，然后被 class_init 覆盖虚函数指针
  • Instance 是类型的 具体对象实例，可以有任意多个，instance_init 负责填充实例特有的字段

1.5 与 GObject 的关系

QOM 的设计受 GLib/GObject 启发但不直接使用 GObject。相似之处：

  • TypeInfo → Class → Instance 三层结构与 GType → GTypeClass → GObject 一一对应
  • class_init / instance_init 的概念与 GObject 的 class_init / instance_init 一致
  • 属性自省受 GObject properties 启发

为什么不直接用 GObject？

  • QEMU 对性能极其敏感，GObject 的 type check 使用信号量，对虚拟化场景太重
  • QEMU 需要 class_size = 0 的语义（子类不新增 class 字段时不需定义 Class 结构），GObject 不支持
  • QOM 需要与 QEMU 的 module 系统、QAPI/QMP 深度集成
  • QEMU 有自己的两阶段构造语义 (instance_init 不可失败 + realize 可失败)，GObject 没有内置这个概念
类比参考： QOM : GObject ≈ C++ vtable : VTBL in MSVC
都是 C 语言级别的虚函数表方案，但 QOM 为了 QEMU 做了大量定制。

1.6 QOM 的边界与约束

QOM 不是一种通用 OOP 框架，它有明确的边界：

约束：
  • instance_init 不能失败（无 Error** 参数）—— 只能做简单字段赋初值
  • realize 才是设备可以失败的构造阶段 —— 它接受 Error**
  • 类型系统是 线程不安全的 —— 类型注册和查找只在主线程
  • Class 对象是 不可变的 —— class_init 只执行一次，之后 class 被所有实例共享
