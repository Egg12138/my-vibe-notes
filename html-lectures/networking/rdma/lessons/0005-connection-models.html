第五课 · RDMA 连接模型

QP 状态机、手工连接与 RDMA CM 事件驱动模型

问题的本质

在第四课中，我们看到数据发送之前 QP 必须处于 RTS（Ready To Send）状态。但 QP 在创建时处于 RESET 状态——它还不能收发数据。要让 QP 进入可工作状态，通信双方必须交换连接元数据，并执行一系列 QP 状态迁移。

这引出一个关键问题：在 QP 可以工作之前，通信双方如何协调？

答案是一个经典的"鸡和蛋"问题：用 TCP 搭建控制通道，在 TCP 上交换 RDMA 连接元数据，然后用这些元数据配置 QP。一旦 QP 建立，TCP 连接可以关闭，后续数据完全走 RDMA。

需要交换的元数据

建立一个 RC QP 连接需要交换以下信息：

字段大小说明
QPN24 位Queue Pair Number，QP 的唯一标识。发送端需要在 BTH 中填入目的 QPN
PSN24 位Packet Sequence Number，起始包序号。用于可靠传输的包排序和去重
LID16 位Local Identifier，子网内地址。对于 RoCEv2，LID 固定为 0
GID128 位Global Identifier，对于 RoCEv2 即为 IP 地址（IPv4-mapped IPv6 格式）
Port隐式设备端口号，大多数单端口设备固定为 1

在手工连接（raw verbs）中，这些信息通过 TCP socket 传输。在 RDMA CM 中，rdma_resolve_addr 会自动处理地址解析和端口选择。

QP 状态机

RC QP 的完整状态迁移路径如下：

RESET → INIT → RTR → RTS → SQD → SQE → ERR

每个 ibv_modify_qp() 调用执行一次状态迁移。每个状态的具体含义：

  • RESET — QP 初始状态，未绑定到任何端口。不能收发任何数据。
  • INIT — QP 绑定到端口和 PD。RQ 可以接收 WQE 提交（可 post_recv），但还不能收发网络数据。设置：qp_attr.qp_state = IBV_QPS_INIT，指定 pkey_index 和 port。
  • RTR（Ready To Receive）— QP 可以接收来自远端的 SEND/RDMA WRITE 数据。但不能发送。设置：本地 QPN、PSN、LID/GID 等对端信息。
  • RTS（Ready To Send）— QP 完全可用，可以发送和接收。设置：发送 PSN、超时参数 timeout、retry_cnt、rnr_retry 等。
  • SQD（Send Queue Drained）— SQ 被排空，用于修改 QP 属性。
  • SQE（Send Queue Error）— SQ 出现错误。
  • ERR — QP 进入错误状态，所有待处理 WR 被 flushed。
实践要点 在 RTR 阶段，你需要知道对端的 QPN、LID、GID 和起始 PSN。这些信息必须通过 TCP 控制通道提前交换。ibv_modify_qp 的参数中任何一项错误（如 GID Index 不对、PSN 不匹配）都会导致连接失败，状态可能卡在 RTR。

方法一：手工 TCP + raw verbs

这种方法在实验中称为"Lab 01"风格。流程如下：

  1. Server 创建 QP（RESET），开始监听 TCP 控制端口
  2. Client 连接 TCP，双方通过 TCP 交换自己的 QPN、GID、LID、PSN
  3. 双方独立调用 ibv_modify_qp：RESET → INIT → RTR → RTS
  4. TCP 连接使命完成，可以关闭
  5. RDMA QP 进入 RTS，开始数据传输

优点：完全透明，让你理解每一比特的连接元数据。缺点：代码量大，容易出错，生产代码极少这样写。

典型代码骨架（伪代码）

// Server 侧: QP 已创建为 RESET
// 1. TCP 接收 Client 的 QPN、GID 等信息
tcp_recv(&remote_qpn, &remote_gid);

// 2. RESET → INIT
ibv_modify_qp(qp, &attr, IBV_QP_STATE | IBV_QP_PKEY_INDEX | IBV_QP_PORT);

// 3. INIT → RTR (填入对端信息)
attr.qp_state = IBV_QPS_RTR;
attr.dest_qp_num = remote_qpn;
attr.path_mtu = IBV_MTU_1024;
attr.ah_attr.grh.dgid = remote_gid;
attr.ah_attr.grh.sgid_index = local_sgid_idx;
ibv_modify_qp(qp, &attr, /* RTR mask */);

// 4. RTR → RTS
attr.qp_state = IBV_QPS_RTS;
attr.timeout = 14;    // 约 5 秒
attr.retry_cnt = 7;   // 无限重试
attr.rnr_retry = 7;   // 无限重试
ibv_modify_qp(qp, &attr, /* RTS mask */);

方法二：RDMA CM（librdmacm）

RDMA CM 封装了整个连接管理过程，自动处理地址解析、QP 创建和状态迁移。在 rdma_connect 调用之后，QP 已经处于 RTS 状态。

Server 侧流程

// 1. 创建 CM ID 和事件通道
rdma_create_event_channel(&cm_channel);
rdma_create_id(cm_channel, &cm_id, NULL, RDMA_PS_TCP);
rdma_bind_addr(cm_id, &bind_addr);
rdma_listen(cm_id, 5);               // 开始监听

// 2. 事件循环：等待 CONNECT_REQUEST
//    在回调中: rdma_create_qp(cm_id, pd) → rdma_accept(cm_id)

// 3. 收到 ESTABLISHED 事件 → 连接就绪，可以 RDMA 通信

Client 侧流程

// 1. 创建 CM ID
rdma_create_event_channel(&cm_channel);
rdma_create_id(cm_channel, &cm_id, NULL, RDMA_PS_TCP);

// 2. 地址解析 (阻塞直到完成)
rdma_resolve_addr(cm_id, &src_addr, &dst_addr, 2000);  // 2s 超时
// 收到 ADDR_RESOLVED 事件

// 3. 路由解析
rdma_resolve_route(cm_id, 2000);
// 收到 ROUTE_RESOLVED 事件

// 4. 连接
rdma_connect(cm_id, &conn_param);
// 收到 ESTABLISHED 事件 → 连接就绪

CM 事件模型

RDMA CM 采用异步事件驱动模型。所有事件必须通过 rdma_ack_cm_event 确认：

事件发起方接收方
ADDR_RESOLVEDrdma_resolve_addr 完成—
ADDR_ERROR地址解析失败—
ROUTE_RESOLVEDrdma_resolve_route 完成—
ROUTE_ERROR路由解析失败—
CONNECT_REQUEST—收到新连接请求
ESTABLISHED连接成功建立连接被对端接受
DISCONNECTED收到断开通知收到断开通知

事件通道的 fd 可以通过 cm_channel->fd 获取，用于集成到 select() / poll() / epoll() 事件循环中。这是实现超时处理的推荐方式——设置 select() 超时，如果事件未在预期时间内到达，可以主动放弃连接。

CM vs 手工：何时用哪种？

场景推荐方式理由
学习 RDMA 连接原理手工 TCP + raw verbs看到每一比特元数据的含义
小型原型或工具RDMA CM代码量减少 70%
生产级应用RDMA CM 或 libfabricCM 处理地址解析和重连，libfabric 提供 provider 抽象
