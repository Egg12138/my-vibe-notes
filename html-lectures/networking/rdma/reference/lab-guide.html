实验指导说明

如何搭建环境、运行实验、使用提示系统与调试工具

实验架构概览

全部六个实验在一组双 QEMU x86_64 虚拟机上进行，两台虚拟机通过独立的虚拟以太网链路互连，每台虚拟机内部通过 Soft-RoCE (RXE) 将普通网卡暴露为 RDMA 设备：

+------------------------------------------------------------------+ | Host (WSL2 / Linux) | | | | +-------------+ +-------------+ | | | Guest 1 | | Guest 2 | | | | (server) | | (client) | | | | | | | | | | rdma link | | rdma link | | | | rxe0 type | | rxe0 type | | | | rxe netdev | | rxe netdev | | | | eth0 | | eth0 | | | | | | | | | | 192.168. | | 192.168. | | | | 100.1/24 | | 100.2/24 | | | +------+------+ +------+------+ | | | | | | | QEMU TCG (no KVM) | | | +-----------------------+ | +------------------------------------------------------------------+
为什么需要两台虚拟机？ RDMA 的"R"代表 Remote。SPD/RECV、RDMA WRITE/READ 等操作要求两端有独立的 RDMA 设备，单机上无法完成。 Soft-RoCE 将内核网络栈模拟为 RNIC，因此可以在无真实硬件的环境中运行标准的 verbs 程序。

每个实验都遵循相同的工作流程：

  1. 先预测：阅读 README 和前置知识后，在 starter/ 中写下对现象的预测
  2. 启动环境：make lab-up LAB=NN 启动双 guest 虚拟机
  3. 观察或实现：运行工具命令观察现象，或完成 starter 中的代码
  4. 验证：make verify LAB=NN 运行自动验收
  5. 制造故障：按实验要求主动引入错误，记录结果
  6. 反思：回答 reflection.md 中的问题，写下结论
  7. 关闭环境：make lab-down 停止并清理虚拟机

内核构建

guest 使用的 Linux 内核需要开启 RDMA 和 Soft-RoCE 支持。内核已预构建（v7.1-rc4），如需手动构建：

# 设置内核源码路径（versions.lock 中锁定）
export RDMA_COURSE_KERNEL_SOURCE=/path/to/linux

# 构建内核
sh scripts/build-kernel.sh

# 产物位于 vm/out/kernel/
#   bzImage       — 可引导内核镜像
#   kernel.config — 实际使用的 .config
#   manifest.lock — 提交和校验和记录

内核配置包含以下关键选项（vm/kernel/required.config）：

配置作用
CONFIG_INFINIBAND=y内核 RDMA 子系统核心
CONFIG_INFINIBAND_USER_ACCESS=y用户态 uverbs ABI（/dev/infiniband/uverbs0）
CONFIG_INFINIBAND_ADDR_TRANS=yRDMA 地址转换 / CM 支持
CONFIG_RDMA_RXE=ySoft-RoCE RXE 驱动
CONFIG_VIRTIO_NET=yQEMU virtio 虚拟网卡
CONFIG_VIRTIO_BLK=yQEMU virtio 虚拟块设备

根文件系统构建

使用 debootstrap 创建 Ubuntu Noble (24.04) ext4 镜像，已包含 rdma-core、perftest、libfabric 等工具：

# 构建 rootfs（需要 sudo，因为 debootstrap 需要 root）
sudo sh scripts/build-rootfs.sh

# 产物位于 vm/out/rootfs/
#   rdma-course.ext4          — 4 GiB ext4 根文件系统镜像
#   rdma-course.ext4.sha256   — 校验和
#   rdma-course.ext4.packages.lock — 已安装包版本清单

rootfs 预装以下关键软件包：

  • RDMA 用户态: rdma-core, ibverbs-utils, librdmacm-utils
  • 开发头文件: libibverbs-dev, librdmacm-dev
  • 基准测试: perftest
  • 生产抽象: libfabric-bin, libfabric-dev, ucx-utils
  • 系统工具: build-essential, cmake, tcpdump, strace, jq
  • 性能分析: linux-tools-generic, numactl

命令行操作指南

课程 Makefile 提供以下统⼀命令。所有命令在仓库根目录下执行。

环境检查

make env-check
# 输出示例：
# required  cmake                     ok
# required  qemu-system-x86_64        ok
# optional  ibv_devices               ok
# optional  rping                     missing
# capability kvm                       missing
# capability rdma-device               missing
# summary   required                  ok

required.missing 表示缺少必选工具，运行实验前需要安装。optional.missing 仅在相关实验中产生影响。KVM 和 RDMA 设备缺失是正常现象（本课程设计为 TCG + Soft-RoCE）。

虚拟机生命周期

# 启动双 guest（实验 NN）
make lab-up LAB=00

# 停止所有 guest
make lab-down

# lab-up 执行以下步骤：
#   1. 启动 guest1（服务端）：前台的 QEMU 实例
#   2. 等待 guest1 启动完成（串口登录检测）
#   3. 在 guest1 内部配置 IP、创建 RXE、启动服务端程序
#   4. 启动 guest2（客户端）
#   5. 在 guest2 内部配置 IP、创建 RXE
# lab-down 执行以下步骤：
#   1. 停止两台 guest 中的用户程序
#   2. 向 QEMU 进程发送 shutdown 或 kill 信号
#   3. 恢复宿主机网络

验证实验

# 验证单个实验
make verify LAB=01

# 验证全部实验（含 host 单元测试）
make verify-all

验证脚本检查 starter 代码是否已完成（无 TODO 残留），然后根据实验类型验证。未完成实验输出明确的 TODO 诊断而不是无说明的编译错误。

获取提示

# 三级提示系统
make hint LAB=01 LEVEL=1   # 概念提示
make hint LAB=02 LEVEL=2   # API / 伪代码提示
make hint LAB=03 LEVEL=3   # 局部代码形状 + 诊断命令

# 提示逐级开放，建议先完成自己能完成的部分，遇到具体障碍再按需查看
提示使用建议： 0 级提示（你的先验知识 + README）永远是最重要的。Level 1 在卡住 15 分钟后再看； Level 2 在实验核心逻辑无法推进时再看；Level 3 只在排错调试阶段参考，不应直接复制。

学习闭环

每个实验强制形成以下反馈回路，这是本课程最核心的学习方法论：

+---------+ +----------+ +----------+ +---------+ | 预测 | --> | 观察/实现 | --> | 自动验收 | --> | 制造故障 | +---------+ +----------+ +----------+ +---------+ | +---------+ +-----------+ +----------+ | | 写下 | <-- | 解释错误 | <-- | 观察现象 | <----+ | 结论 | | | | | +---------+ +-----------+ +----------+
  1. 预测：先动脑，写下你的假设，再动工具
  2. 观察：用工具（ibv_devices、rping、tcpdump、perftest）收集证据
  3. 实现：在 starter 中完成代码
  4. 验收：make verify 自动检查
  5. 故障注入：故意破坏参数/权限/连接顺序，观察失败模式
  6. 解释：用 CQ 事件、CM 状态、资源计数器或抓包解释错误根因
  7. 写下：完成 reflection.md，记录结论而不是"测试通过"
关键原则： 不要跳过"预测"和"故障注入"。只看正确路径会让你错误地以为自己理解了 RDMA。 真正理解 RDMA 的标志是：你能制造一个故障，然后在不用看代码的情况下预测出 WC status 是什么、CM 会触发哪个错误事件、资源计数器会如何变化。

故障排查快速参考

常见问题的排查入口（详细诊断请参考 故障诊断指南）：

症状可能原因首先检查
ibv_devices 为空 RXE 未加载或 link 未创建 lsmod | grep rdma_rxe → rdma link show
ibv_modify_qp 失败 参数错误 / 端口未 ACTIVE / MTU 不匹配 ibv_devinfo → 检查端口状态和 MTU
rping 连接超时 服务端未启动 / 端口不通 / 防火墙 ping 确认 IP 连通性 → ss -tlnp 确认监听
WC status != SUCCESS rkey 错误 / 权限不足 / 未 post recv 检查 WC 状态码 → 参考故障诊断页面的状态码表
RDMA WRITE 无效果 忘记 IBV_ACCESS_REMOTE_WRITE rdma resource show 查看 MR 权限
性能数据异常低 TCG + Soft-RoCE 固有瓶颈 只比较相对趋势，不宣称绝对数字
资源泄漏检测: rdma resource show 可以显示当前所有 QP、MR、CQ、PD 的计数。 实验 03 要求重复运行 20 次不残留资源。

实验顺序与依赖

实验严格按照 00 → 05 顺序完成：

  • 00 是纯观察实验，不需要写代码。建立基础设备概念和操作肌肉记忆
  • 01 使用手动 TCP 交换 QP 元数据，让你看见 raw verbs 没有替你解决连接协商
  • 02 在 01 的 RC QP 基础上增加 MR/rkey 和单边操作
  • 03 用 RDMA CM 替换 01/02 中的 TCP 控制通道，对比两种连接管理方式
  • 04 使用 perftest 和 perf 工具，不改变代码但改变参数和方法论
  • 05 用 libfabric provider 抽象重做 02 的 mailbox 功能，对比 raw verbs 和抽象层
设计动机：先暴露问题（手动交换元数据太麻烦），再给出解决方案（RDMA CM）， 再提出新问题（provider 锁死），再给出更高抽象（libfabric/UCX）。 每一课的"为什么"由前一课的实际体验回答。
