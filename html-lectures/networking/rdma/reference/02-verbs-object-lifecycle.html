Verbs 对象生命周期

Context、PD、MR、CQ、QP 的创建依赖与销毁顺序

对象依赖图

RDMA verbs 对象之间存在严格的依赖层次。下层对象必须在上层对象销毁之后才能释放。违反这一规则会导致内核错误（EBUSY）、use-after-free、或驱动崩溃。

+----------+ | Device | 物理 RDMA 设备 (HCA / RXE) +----+-----+ | v +----------+ | Context | ibv_context, 通过 ibv_open_device 获得 +----+-----+ | +------+------+ | | | v v v +-------+ +-------+ +-------+ | PD | | CQ | | SRQ | +---+---+ +-------+ +-------+ | | +---+---+ | | | | v v v +-----+ +-----+ | MR | | QP | +-----+ +-----+ 依赖方向: 创建时 上层 -> 下层 销毁时 下层 -> 上层 (逆序) 典型创建顺序: 1. ibv_get_device_list / ibv_open_device → Context 2. ibv_alloc_pd(context) → PD 3. ibv_create_cq(context) → CQ 4. ibv_reg_mr(pd, ...) → MR 5. ibv_create_qp(pd, &qp_init_attr) → QP (需要 PD + CQ) 典型销毁顺序: 1. ibv_destroy_qp(qp) 2. ibv_dereg_mr(mr) 3. ibv_destroy_cq(cq) 4. ibv_dealloc_pd(pd) 5. ibv_close_device(context)

Context (ibv_context)

Context 是应用与特定 RDMA 设备之间通信的句柄。它代表一个 /dev/infiniband/uverbsX 文件描述符的打开实例。

创建

struct ibv_device **dev_list;
struct ibv_context *ctx;

dev_list = ibv_get_device_list(&num_devices);   // 枚举所有 RDMA 设备
if (!dev_list || num_devices == 0) { /* 无设备 */ }

ctx = ibv_open_device(dev_list[0]);              // 打开第一个设备
if (!ctx) { /* 打开失败 */ }

ibv_free_device_list(dev_list);                  // 释放设备列表，但 ctx 仍有效

属性

字段说明
device指向 ibv_device 的指针，描述物理设备信息
cmd_fduverbs 字符设备的文件描述符
opsprovider 实现的操作函数表（ABI 封装）
abi_compat内核与用户态 AB 版本 compat 信息

销毁

调用 ibv_close_device(ctx)。这是最后一步关闭的句柄。所有从该 context 派生出的对象必须先被销毁。

常见问题 多个 context 可以指向同一设备（多进程场景），但每个 context 有独立的对象空间。一个进程内不应同时对同一设备打开大量 context，这会导致内核文件描述符耗尽。

Protection Domain (ibv_pd)

PD 是 RDMA 的安全隔离域。MR、QP、AH 都必须绑定到一个 PD。同一 PD 内的对象可以互相访问；跨 PD 访问需要 rkey 授权。

struct ibv_pd *pd = ibv_alloc_pd(ctx);
if (!pd) { /* 分配失败 */ }

// ... 使用 pd 创建 MR、QP ...

ibv_dealloc_pd(pd);   // 销毁，调用前确保所有 MR 已 deregister，所有 QP 已 destroy

PD 的语义作用

  • 安全隔离 — QP 只能访问同一 PD 下的 MR。进程 A 的 QP 无法直接访问进程 B 的 MR（除非跨 PD 传递 rkey）。
  • 资源分组 — 多租户场景中，不同租户使用不同 PD，防止相互干扰。
  • 性能 — PD 切换对 HCA 是昂贵的操作（TLB 刷新）。应尽量复用 PD 而非频繁创建销毁。

Memory Region (ibv_mr)

MR 将一段用户态虚拟内存注册到 HCA，使其可被 RDMA 操作访问。

struct ibv_mr *mr = ibv_reg_mr(pd, buf, size,
                                IBV_ACCESS_LOCAL_WRITE |
                                IBV_ACCESS_REMOTE_WRITE |
                                IBV_ACCESS_REMOTE_READ);
if (!mr) { /* 注册失败 */ }

// mr->lkey  — 本地操作 (post_send 的 sge.lkey)
// mr->rkey  — 远程操作 (RDMA WRITE/READ 时对端使用)

ibv_dereg_mr(mr);     // 注销 MR，释放 pinning 的内存页

MR 属性

字段说明
addrMR 起始虚拟地址（原传的 buf 地址）
lengthMR 大小 (bytes)
lkeyLocal Key，本地操作时使用
rkeyRemote Key，远程 RDMA WRITE/READ 时使用
pd所属 Protection Domain

生命周期注意事项

  • ibv_dereg_mr() 会 unpin 之前 pinning 的内存页。如果之后还有 QP 使用这些页做 DMA，会导致数据损坏。
  • 注销 MR 之前必须确保没有正在执行的 WR 引用该 MR。
  • MR 的权限（IBV_ACCESS_REMOTE_WRITE 等）在注册时决定，后续无法修改。需要新权限需 deregister 后重新注册。

Completion Queue (ibv_cq)

CQ 存放 Work Completion (WC)。Send 和 Recv 完成的通知都发到同一个 CQ（或不同 CQ，取决于创建时的配置）。

struct ibv_cq *cq = ibv_create_cq(ctx, cqe, NULL, NULL, 0);
// cqe: CQ 容量（可容纳的 WC 数量）
// 参数 3: cq_context (ibv_get_cq_event 时返回)
// 参数 4: channel (Completion Event Channel)
// 参数 5: comp_vector (MSI-X 中断向量索引)

if (!cq) { /* 创建失败 */ }

// ... 将 cq 关联到 QP 的 send_cq 和/或 recv_cq ...

ibv_destroy_cq(cq);   // 销毁，所有关联 QP 必须先 destroy

CQ 参数选择

参数建议说明
cqe 数量QP 总数 × Queue Depth × 2WC 溢出会导致严重的性能下降。CQ 满时新完成的 WQE 无法写入，可能触发异步错误。
comp_vector= qp_index % num_comp_vectors中断亲和性，将 CQ 绑定到不同 CPU 可分摊中断处理
channelNULL 使用轮询模式如果只需要 ibv_poll_cq 轮询，传 NULL。需要事件通知时需要创建 ibv_comp_channel

Queue Pair (ibv_qp)

QP 是 RDMA 通信的核心对象。每个 QP 包含两个子队列：Send Queue 和 Receive Queue。

struct ibv_qp_init_attr attr = {
    .qp_context = NULL,
    .send_cq = cq,
    .recv_cq = cq,         // send 和 recv 可用同一个 CQ
    .srq = NULL,           // 使用独立 RQ（非 SRQ）
    .cap = {
        .max_send_wr  = 128,
        .max_recv_wr  = 128,
        .max_send_sge = 1,
        .max_recv_sge = 1,
        .max_inline_data = 0,
    },
    .qp_type = IBV_QPT_RC,
};

struct ibv_qp *qp = ibv_create_qp(pd, &attr);
if (!qp) { /* 创建失败 */ }

// ... 修改 QP 状态: RESET -> INIT -> RTR -> RTS ...

ibv_destroy_qp(qp);   // 销毁。必须先于 CQ 和 PD 的销毁

QP 属性

字段说明
qp_numQP 编号，对端在 INIT→RTR transition 时需要知道
pd所属 PD
send_cq / recv_cq发送/接收完成的 CQ，可以相同
qp_typeRC / UC / UD / XRC / RAW_PACKET
state当前 QP 状态
sq / rq发送/接收队列深度和 sge 限制

销毁顺序规则

RDMA 对象销毁必须 严格按照依赖关系的逆序 执行。原因在于每个对象都持有对上层对象的引用。如果先销毁父对象，子对象可能仍在硬件中存有 DMA 操作引用。

// ==== 推荐销毁顺序 ====

// 第 1 步: 销毁所有 QP
rc = ibv_destroy_qp(qp);
if (rc) { /* 失败: QP 可能仍有未完成的 WR */ }

// 第 2 步: 注销所有 MR
rc = ibv_dereg_mr(mr);
if (rc) { /* 失败: MR 可能仍被 QP 引用 */ }

// 第 3 步: 销毁 CQ
rc = ibv_destroy_cq(cq);
if (rc) { /* 失败: CQ 不为空或仍有 QP 关联 */ }

// 第 4 步: 释放 PD
rc = ibv_dealloc_pd(pd);
if (rc) { /* 失败: PD 下仍有 MR 或 QP */ }

// 第 5 步: 关闭设备
rc = ibv_close_device(ctx);
if (rc) { /* 失败: 关闭问题 */ }
为什么必须逆序？ 每层对象销毁时都会检查子对象列表。例如 ibv_destroy_qp() 会在内核中将 QP 标记为正在销毁，确保 HCA 不会再处理该 QP 的 DMA 操作。ibv_dereg_mr() 会 unpin 内存页。如果先 dereg MR 而 QP 仍在工作，HCA 的 DMA 操作可能访问已经 unpin 的页面，导致数据损坏或 IOMMU 错误。

常见错误与诊断

错误症状根因
EINVAL on destroy_qpibv_destroy_qp() 返回 -1, errno = EINVALQP 处于错误状态且有未完成的 WR。需先将 QP 移到 RESET 再 destroy。
EBUSY on dealloc_pdibv_dealloc_pd() 返回 EBUSYPD 下仍有未销毁的 MR 或 QP。检查销毁顺序。
ENOMEM on reg_mrMR 注册失败，内存不足进程 locked memory 限制 (ulimit -l) 太低。MR 注册需要 pinning 内存页。
Segfault after dereg_mr应用 segfault 或数据损坏QP 仍然引用已注销的 MR。确保所有依赖该 MR 的 WR 已完成再 dereg。
CQ 溢出 (WC_WR_FLUSH_ERR)WC 状态为 IBV_WC_WR_FLUSH_ERRCQ 深度不足。当 CQ 满时新完成的 WQE 被丢弃，相关 WR 返回 flush 状态。
QP 创建失败ibv_create_qp() 返回 NULL可能是 PD 不匹配或 CAP 参数超出设备限制。检查 ibv_query_device() 的设备能力。
调试建议 使用 ibv_devinfo 命令查看设备能力、端口状态、GID 表。使用 cat /sys/class/infiniband/*/device/num_comp_vectors 查看中断向量数。异常时检查 dmesg 中的 RDMA 子系统报错。
