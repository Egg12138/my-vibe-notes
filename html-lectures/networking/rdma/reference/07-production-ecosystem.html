生产 RDMA 生态

libfabric、UCX、MPI、NCCL 的抽象层次与适用场景

抽象层次

RDMA 在不同的开发场景下被不同层次的库封装。从最底层到最上层：

+-----------------------------------------------------------+
|  应用层                                                       |
|  MPI (OpenMPI/MPICH)  |  NCCL  |  SHMEM  |  自定义服务      |
+--------------------------------------+--------------------+
|  中间库层                                                   |
|  UCX (UCP + UCT)      |  libfabric (OFI)                  |
|  - 自动传输选择        |  - provider 抽象                   |
|  - 协议/传输/服务三层   |  - FI_EP_MSG/RDM/DGRAM           |
+--------------------------------------+--------------------+
|  连接管理层                                                   |
|  librdmacm (RDMA CM)                                       |
|  - 地址/路由解析       |  - 连接建立/断开    |  - 多播      |
+--------------------------------------+--------------------+
|  核心 Verbs 层                                               |
|  libibverbs (raw verbs)                                     |
|  - ibv_reg_mr / ibv_post_send / ibv_poll_cq                |
|  - 直接控制 QP/PD/MR/CQ                                    |
+--------------------------------------+--------------------+
|  驱动层                                                      |
|  rdma-core 用户态驱动   |  内核 ib_uverbs  |  HCA 固件      |
+-----------------------------------------------------------+

层次越高，抽象度越高，但控制力和灵活性也随之降低。选择哪一层取决于你的目标：学习 RDMA 原理 → raw verbs；构建可移植生产服务 → libfabric/UCX；科学计算 → MPI。

libfabric（OFI）

libfabric 是 Open Fabrics Interface（OFI）项目的参考实现，旨在提供 provider 无关的 RDMA 编程接口。同一个应用程序无需修改代码即可在不同互连（InfiniBand、RoCE、iWARP、EFA、Cray 等）上运行。

Provider 模型

Provider 底层传输 典型场景
tcp TCP socket 开发调试，无 RDMA 硬件时的回退
verbs;ofi_rxm libibverbs（RC QP + RXM 消息层） 通用 RDMA，自动处理消息分段/重组
verbs libibverbs（直接映射） 需要精细控制的消息传递
sockets TCP socket（独立实现） 跨平台兼容性测试
shm 共享内存 节点内通信（无网络开销）
efa AWS Elastic Fabric Adapter（SRD 协议） AWS 云环境的 HPC/ML
psm2 Intel OmniPath PSM2 Intel OPA 集群

核心对象与端点类型

libfabric 的对象层次结构：FI_FABRIC → FI_DOMAIN → FI_EP。端点（Endpoint）是通信的入口点：

端点类型 语义 对应 QP 类型
FI_EP_MSG 面向连接的消息传递（connected message） RC（Reliable Connection）
FI_EP_RDM 可靠数据报（reliable datagram） RC 多连接模拟，或 DCT（Dynamic Connected Transport）
FI_EP_DGRAM 不可靠数据报（unreliable datagram） UD（Unreliable Datagram）

能力发现机制：

struct fi_info *info;
fi_getinfo(FI_VERSION(2, 0), NULL, 0, 0, &info);
/* 检查 info->caps 是否包含 FI_MSG, FI_RMA, FI_TAGGED, FI_ATOMIC */

应用程序在初始化时查询 provider 的能力集，动态选择实现路径。这使provider 切换无需代码变更——只需通过环境变量 FI_PROVIDER=efa 或 FI_PROVIDER=verbs 指定。

UCX（Unified Communication X）

UCX 是 HPC 社区的中间件标准。它由三个子框架组成：

  • UCP（Unified Communication Protocols）：协议层，提供消息传递、RMA、AMO 等高阶 API。
  • UCT（Unified Communication Transports）：传输层，封装不同硬件后端，如 RC、UD、DC、TCP、shared memory。
  • UCS（Unified Communication Services）：服务层，提供通用工具如配置解析、日志、内存管理。

传输选择与工具

UCX 支持多种 RDMA 传输，且可以自动选择最优传输路径：

# 查看系统上可用的传输层
ucx_info -d

# 输出示例（节选）：
# # Transport: ib
# # Device: ibp0s2
# #   type: RC
# #   bandwidth: 12.5 GB/sec
# #   latency: 2.5 usec
# # Transport: shm
# #   type: shared memory
# #   bandwidth: 40 GB/sec
# #   latency: 0.3 usec

# 运行基准测试
ucx_perftest -c 0 -t tag_lat -n 100000

UCP 协议层会在 ucp_ep_create 时根据通信双方的距离和硬件能力自动选路：同一 NUMA 节点 → shm；跨节点 RDMA 可达 → RC/DC；跨网络 → TCP。

MPI 与 RDMA

MPI（Message Passing Interface）是科学计算的事实标准。现代 MPI 实现（OpenMPI、MPICH、MVAPICH）都基于 RDMA 构建：

实现 底层传输层 特点
OpenMPI UCX（默认）或 libfabric BTL（Byte Transfer Layer）插件化；支持 IB、RoCE、iWARP
MPICH CH4 设备 + UCX/libfabric/netmod 与 OpenMPI 对齐 UCX 作为统一传输层
MVAPICH raw verbs（手动优化） 对 Mellanox 硬件深度优化，最早支持 GPU Direct RDMA

MPI 的点对点通信利用 RDMA 的方式：

  • Eager 协议（小消息，< 阈值）：使用 SEND/RECV，数据被复制到预分配的 eager buffer 中。
  • Rendezvous 协议（大消息，> 阈值）：使用 RDMA WRITE 直接将数据写入对端缓冲区，零拷贝。
  • Collective 操作：Allreduce、Alltoall、Barrier 等利用 RDMA 做多播/归约加速。

NCCL 与 GPU Direct

NVIDIA NCCL（NVIDIA Collective Communication Library）专为 GPU 间通信优化：

  • GPU Direct RDMA：允许 NIC 直接读写 GPU 显存，无需经过主机内存中转。数据路径：GPU 显存 → PCIe → NIC → 网络。
  • PCIe 拓扑感知：NCCL 自动发现 GPU-NIC 之间的 PCIe 拓扑，选择最短路径（如同一个 PCIe switch 下的 GPU 和 NIC 之间延迟最低）。
  • Ring / Tree 算法：NCCL 使用 ring allreduce 或 tree allreduce 算法，将 GPU 间通信负载均摊。

GPU Direct RDMA 要求：

# 硬件要求
- NVIDIA GPU（Kepler 或更新） + 支持 BAR1 的驱动
- RDMA NIC（Mellanox ConnectX-5+ 或同类）
- 同一 PCIe root complex 下（最优）；或通过 PCIe switch 连接

# 软件要求
- nvidia-p2p 内核模块（提供 GPU 物理地址到 BAR 地址的映射）
- CUDA 11.0+
- nvidia-fabricmanager（多 GPU 互联时）

GPU 显存注册与主机内存不同：GPU 内存是非一致性内存（non-coherent），需要使用 nvidia_p2p_get_pages 获取物理地址映射，再通过 ibv_reg_mr 注册——但这超出了标准 Verbs 接口，实际由 NCCL 内部封装。

选择指南

场景 推荐层 理由
学习 RDMA 原理 raw verbs（libibverbs） 最底层、最清晰的 API，直接暴露所有概念和开销。
快速搭建原型 RDMA CM + raw verbs CM 处理连接管理，verbs 处理数据面——平衡开发速度和底层控制。
生产服务（可能换硬件） libfabric provider 模型保证抽象层不变，切换硬件只需换 provider 参数。
HPC / ML 训练 UCX 自动传输选择、活跃社区、广泛用于 HPC 和深度学习框架。
科学计算 MPI on UCX/libfabric MPI 标准、丰富的 collectives、成熟调试工具。
GPU 分布式训练 NCCL NVIDIA 官方库，GPU Direct RDMA 深度优化，PyTorch/TensorFlow/JAX 原生集成。

云环境

云平台 RDMA 方案 说明
AWS EFA（Elastic Fabric Adapter） libfabric EFA provider，使用 SRD（Scalable Reliable Datagram）协议——类似 UD 但带重传。支持 OS-bypass，延迟 ~10 μs。需 EFA-enabled 实例类型。
Azure InfiniBand（SR-IOV） HPC SKU（HC, HB, ND 系列）提供直通 InfiniBand。通过 ConnectX 驱动直接暴露，App 无感。
GCP 无标准 RDMA 标准 VM 不提供 RDMA 设备。GKE 使用 gVNIC + TCP，不暴露 /dev/infiniband/ 给用户。

容器场景：Kubernetes 中暴露 RDMA 设备需要 device plugin（如 Mellanox 的 k8s-rdma-sriov-device-plugin）。容器需挂载 /dev/infiniband/* 并设置 IPC namespace 为 host（共享内存通信）。Pod 之间无法共享 RDMA 设备——每个 Pod 需要独立的 SR-IOV VF 或完整的 PCIe passthrough。

存储生态

RDMA 在存储领域有广泛的应用：

  • NVMe-oF（NVMe over Fabrics）：将 NVMe 命令封装在 RDMA 上传输。典型延迟 5-10 μs，带宽 100 Gbps+。Linux 内核内置 nvme-rdma 驱动。
  • SPDK（Storage Performance Development Kit）：用户态的 NVMe-oF target 实现。完全绕过内核，使用轮询（polling）而非中断，进一步提升 IOPS。
  • NFSoRDMA（NFS over RDMA）：NFS v4.1+ 支持以 RDMA 作为传输层。通过 rdma 挂载选项启用。
  • Ceph：Ceph 的 RDMA messenger 目前为实验性功能，通过 AsyncMessenger + RDMAStack 实现。主要瓶颈是 Ceph 自身的 OSD 处理延迟。
  • iSER（iSCSI Extensions for RDMA）：将 iSCSI 协议跑在 RDMA 上，消除 iSCSI 的 TCP 拷贝开销。
