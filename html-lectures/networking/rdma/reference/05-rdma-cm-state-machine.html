RDMA CM 状态机

地址解析、路由解析、连接建立与断开的异步事件模型

为什么需要 RDMA CM

Raw verbs 提供了对 HCA 硬件的完全控制权，但它不处理任何网络层任务：

  • 地址解析：将目标主机名或 IP 地址转换为 RDMA 设备可理解的 GID（Global Identifier）。
  • 路由解析：确定从本机到目标 Node 的路径——在 InfiniBand 子网中，这涉及 SM（Subnet Manager）查询和路径记录。
  • 连接建立：为 RC（Reliable Connection）QP 完成握手——交换 QPN、PSN、MTU 等参数。
  • 断开通知：监听并报告对端断开、设备移除等异常。
  • 多播（Multicast）：加入/离开 InfiniBand 或 RoCE 的多播组。

librdmacm 封装了上述逻辑，提供类似 TCP socket 的编程模型。它基于 libibverbs 构建，自身不管理数据传输——只管理连接状态。数据面仍由 raw verbs（ibv_post_send / ibv_post_recv）完成。

核心对象

对象 类型 说明
rdma_event_channel struct rdma_event_channel * 异步事件投递通道。所有 CM 事件（连接请求、建立、断开等）都通过此 channel 传递给用户。其 fd 字段可被 poll / select 监听。
rdma_cm_id struct rdma_cm_id * 连接标识符，相当于 socket fd + 本地 fabric 端口的组合。封装了底层的 QP（若有）。每个 cm_id 绑定一个事件 channel。
rdma_create_ep 辅助函数 简化创建流程：rdma_create_ep 内部创建 channel + id + 绑定，一步到位。适用于不需要精细控制的事件驱动的应用。
rdma_getaddrinfo 辅助函数 类似 getaddrinfo(3)，返回 struct rdma_addrinfo，包含源地址、目标地址以及源 RDMA 设备信息。

Server 事件序列

1. chan = rdma_create_event_channel()
2. id = rdma_create_id(chan, ...)
3. rdma_bind_addr(id, bind_addr)
4. rdma_listen(id, backlog)
5. chan 上等待 CONNECT_REQUEST 事件
6. rdma_get_cm_event(chan, &event)       ← CONNECT_REQUEST
7. rdma_create_qp(id, pd, ...)           ← 为连接创建 QP
8. rdma_accept(child_id, ...)
9. chan 上等待 ESTABLISHED 事件
10. rdma_get_cm_event(chan, &event)      ← ESTABLISHED
11. 数据传输（ibv_post_send / ibv_post_recv）
12. rdma_disconnect(id)
13. chan 上等待 DISCONNECTED 事件
14. rdma_get_cm_event(chan, &event)      ← DISCONNECTED
15. 清理：rdma_destroy_qp → rdma_destroy_id → rdma_destroy_event_channel

关键细节：

  • rdma_listen 的 backlog 参数类似 TCP listen backlog，控制未完成 accept 连接的队列深度。
  • CONNECT_REQUEST 事件返回的 child_id 是一个新的 cm_id，需为其创建独立的 QP。
  • rdma_accept 可附带 rdma_conn_param：设置 initiator_depth、responder_resources、rnr_retry_count 等。
  • 每个事件必须通过 rdma_ack_cm_event 确认（ack），否则后续事件不会到达。

Client 事件序列

1. chan = rdma_create_event_channel()
2. id = rdma_create_id(chan, ...)
3. rdma_resolve_addr(id, src, dst, timeout_ms)  ← 地址解析
4. chan 上等待 ADDR_RESOLVED 事件
5. rdma_get_cm_event(chan, &event)              ← ADDR_RESOLVED
6. rdma_resolve_route(id, timeout_ms)            ← 路由解析
7. chan 上等待 ROUTE_RESOLVED 事件
8. rdma_get_cm_event(chan, &event)              ← ROUTE_RESOLVED
9. rdma_create_qp(id, pd, ...)
10. rdma_connect(id, conn_param, ...)
11. chan 上等待 ESTABLISHED 事件
12. rdma_get_cm_event(chan, &event)             ← ESTABLISHED
13. 数据传输
14. rdma_disconnect(id)
15. chan 上等待 DISCONNECTED 事件
16. rdma_get_cm_event(chan, &event)             ← DISCONNECTED
17. 清理

客户端必须先完成地址和路由解析，再创建 QP 和发起连接——这与 TCP 的 connect(2) 不同，因为 RDMA 需要预先知道出向接口和路径 MTU。

推荐实践：使用 rdma_getaddrinfo 替代手动填充地址信息。它自动处理 IPv4/IPv6 → GID 转换、查找正确的 RDMA 设备并填充源地址。设置 hints.ai_port_space = RDMA_PS_TCP 用于 RC 连接。

错误事件

事件 原因 排查方向
ADDR_ERROR rdma_resolve_addr 失败——主机名无法解析、源地址不属于任何 RDMA 设备、目标地址不可达。 检查主机名/DNS 配置；确认 RDMA 设备存在且端口 UP；用 ibv_devinfo 查看设备。
ROUTE_ERROR rdma_resolve_route 失败——子网中无有效路径，或超出子网范围。 检查 ip route；确认两台机器在同一 IB 分区（InfiniBand P_Key）；确认 SM 运行正常。
CONNECT_ERROR 连接建立阶段失败——QPN/PSN 协商失败，或对端拒绝连接。 检查防火墙是否放行 CM 端口（默认端口 3891 或 RoCE 的 UDP 4791）；确认对端在 listen。
UNREACHABLE 对端网络不可达——可能是底层链路故障。 用 ibping 测试 InfiniBand 可达性；检查链路层状态（ibstat 确认 LinkUp）。
REJECTED 对端主动拒绝连接——端口未监听或 conn_param 参数不匹配。 确认对端 rdma_listen 已调用且端口正确；ss -tlnp 查 CM 端口。
DEVICE_REMOVAL HCA 设备被热拔出或驱动卸载。 通知应用层做优雅关闭，释放所有资源。

超时管理

RDMA CM 的地址和路由解析支持显式超时：

int ret = rdma_resolve_addr(id, src, dst, 2000);   /* 2 秒超时 */
if (ret) { perror("rdma_resolve_addr"); exit(1); }

但 CM 自身不提供通用的 "连接超时" 机制——rdma_connect 本身不会超时。你必须使用 poll 或 select 在事件 channel 的 fd 上监听：

struct pollfd pfd = { .fd = chan->fd, .events = POLLIN };
int n = poll(&pfd, 1, 5000);   /* 5 秒整体超时 */
if (n == 0) {
    fprintf(stderr, "连接超时\n");
    rdma_disconnect(id);
    goto cleanup;
}
/* 有事件到达，调用 rdma_get_cm_event */

常见超时策略：

  • 地址解析：3-5 秒。失败一般是配置错误。
  • 路由解析：3-5 秒。失败可能是网络拓扑变化。
  • 连接建立：10-30 秒。取决于对端状态和网络延迟。
  • 断开等待：3-5 秒。对端可能不会立即响应。

清理规则

RDMA CM 资源清理必须遵循严格的顺序，否则会导致资源泄漏或 panic：

  1. 每个 CM 事件必须 ack：调用 rdma_ack_cm_event 释放内核事件队列空间。未 ack 的事件会阻塞后续事件投递。
  2. 先销毁 QP，再销毁 cm_id：rdma_destroy_qp(cm_id) 必须在 rdma_destroy_id(cm_id) 之前。因为 destroy_id 会尝试在清理硬件资源时引用 QP。
  3. 先销毁 cm_id，再销毁 event channel：event channel 上可能还有未处理事件，先销毁 cm_id 可确保事件队列被 drain。
  4. 幂等清理：始终检查指针为空再调用 destroy 函数，并在 destroy 后将指针置 NULL：
if (qp) { rdma_destroy_qp(qp); qp = NULL; }
if (cm_id) { rdma_destroy_id(cm_id); cm_id = NULL; }
if (chan) { rdma_destroy_event_channel(chan); chan = NULL; }
调试技巧：如果在清理时报 ENOMEM 或 EBUSY，通常是事件未 ack 或 QP 仍在活动状态。用 rdma resource show 查看残留的 QP 和 CM_ID。

CM vs 手工 TCP

在 lab 01 中，我们用手工搭建 TCP 连接交换 QPN/PSN/GID。CM 将此过程自动化：

方面 手工 TCP 方式 RDMA CM
地址解析 手动配置 GID、IP 地址 rdma_resolve_addr + rdma_getaddrinfo
路由解析 不处理 rdma_resolve_route 自动查询路径
连接握手 自定义 TCP 协议交换 QPN/PSN CM 内核模块处理握手协议
错误处理 需自行解析断开原因 结构化的事件类型（REJECTED, UNREACHABLE 等）
多播 不支持 rdma_join_multicast / rdma_leave_multicast

CM 的内部实现因链路层而异：

  • InfiniBand：通过内核 CM 模块（ib_cm）使用 InfiniBand 的 CM 协议做 REQ/REP/RTU 三次握手。
  • RoCE：通过 rping 风格在 IP 上封装 CM 消息，本质是 TCP + RoCE 地址交换。
  • iWARP：通过 MPA（Marker PDU Aligned framing）协商连接。
