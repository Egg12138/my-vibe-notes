RDMA 故障诊断指南

设备发现、QP 状态、连接建立与性能异常的排查流程

诊断工具箱

以下命令是 RDMA 故障诊断的必备工具。面对任何 RDMA 异常，先从头到尾跑一遍：

命令 用途 关键输出
ibv_devices 列出所有 RDMA 设备 设备名列表。空输出 = 驱动未加载或未发现设备。
ibv_devinfo 详细的设备信息和端口属性 端口状态（PORT_ACTIVE/INIT/DOWN）、MTU、GID 列表、max_qp/max_mr/max_cq 等资源上限。
rdma link show 查看 RDMA 链路状态（rdma-core 新版） RXE 设备状态和绑定的 netdev。
rdma resource show 显示系统级 RDMA 资源使用量 QP / MR / CQ / PD 数量。可加 qp / mr / cm_id 子命令查看详情。
ibstat InfiniBand HCA 物理端口状态 物理状态（LinkUp/LinkDown）、逻辑状态（Actice/Init/Arm）、速率（FDR/EDR/HDR）。
perfquery InfiniBand 性能计数器 符号错误计数、链路 CRC 错误、缓冲区超限等。
tcpdump -i eth0 udp port 4791 捕获 RoCEv2 流量（RoCEv2 封装在 UDP） 验证报文长度、序列号、是否有重传。
strace -e trace=ioctl,writev,readv 跟踪控制路径 syscall 确认 ibv_reg_mr 是否调用了 mmap/ ioctl。不要对数据路径做 strace！
dmesg | grep -iE "rxe|infiniband|mlx|rdma" 内核 RDMA 错误消息 模块加载失败、RXE 注册错误、HCA 固件异常。
rdma statistic show per-QP 的统计计数器 发送/接收字节数、错误包数、重传次数。
快速检查清单： ibv_devices 能看到设备吗？→ ibv_devinfo 端口是 ACTIVE 吗？→ 两端都能 ping 通吗？→ rdma resource show 有资源泄漏吗？→ dmesg 有错误吗？从头排查，每一步都不要猜。

设备不可见

ibv_devices 输出为空或缺少预期设备。

原因 检查方法 修复
内核模块未加载 lsmod | grep rdma_rxe（Soft-RoCE）或 lsmod | grep mlx（Mellanox） sudo modprobe rdma_rxe 或 sudo modprobe mlx5_ib
RXE 链路未创建 rdma link show 无 rxe 设备 sudo rdma link add rxe0 type rxe netdev eth0
权限拒绝 ls -l /dev/infiniband/* 属主是 root 将用户加入 rdma 组，或添加 udev 规则：
SUBSYSTEM=="infiniband", MODE="0666"
rdma-core 未安装 dpkg -l | grep rdma-core 空 sudo apt install rdma-core ibverbs-utils perftest
网卡不支持 RoCE ethtool -i eth0 驱动不是 mlx/irdma/qedr 确认网卡型号。普通 Intel/Realtek 网卡不支持。使用 Soft-RoCE（RXE）模拟。
常见陷阱：创建 RXE 链路后 ibv_devinfo 显示端口为 PORT_INIT 而非 PORT_ACTIVE。这通常是因为绑定的 netdev 未处于 UP 状态。先 ip link set eth0 up，再重新创建 RXE 链路。

QP 状态卡住

ibv_post_send 返回错误，或 QP 状态转换卡在 INIT/RTR。

# 检查 QP 状态（以 pid 为单位）
rdma resource show qp -j | python3 -m json.tool

# 或者手动用 ibv_devinfo 确认端口信息
ibv_devinfo -d rxe0 | grep -A5 port
WC 状态 含义 常见原因
IBV_WC_RETRY_EXC_ERR 重试次数耗尽 对端 QP 未建立、路径 MTU 设置过大、丢包
IBV_WC_RNR_RETRY_EXC_ERR RNR 重试次数耗尽 对端未及时 posted RECV，或 rnr_retry 计数设置过小
IBV_WC_REM_ACCESS_ERR 远端访问权限错误 rkey 无效或 access flags 不包含所需操作

GID 不匹配是 RoCEv2 中最常见的配置错误：

# 查看 GID 表
ibv_devinfo -d rxe0 | grep GID

# 用 ibv_query_gid 编程查看
# 确保两端使用的 GID index 一致
快速修复：总是用 ibv_modify_qp 的 IBV_QP_STATE 属性并检查返回值。将 QP 状态转换打印到日志：fprintf(stderr, "modify_qp to %s: %s\n", state_name, strerror(errno));。

连接建立失败

rping 或 ib_send_bw 无法连接。

CM 事件 常见原因 排查步骤
ADDR_ERROR 主机名无法解析、源地址不属于任何 RDMA 设备、RDMA 设备不存在 ibv_devices 确认设备存在。rdma_getaddrinfo 是否返回正确结果？
ROUTE_ERROR 没有到目标的路由，或在 InfiniBand 子网中找不到路径 ip route get DEST_IP 确认路由存在。ibping 测试 IB 层可达性。
REJECTED 对端未在目标端口 listen，或 conn_param 不匹配 ss -tlnp | grep 3891 确认 server 在监听。rdma_conn_param 中的 responder_resources 是否足够？
CONNECT_ERROR CM 握手失败——防火墙或子网配置 确认 CM 端口（默认 3891）未被防火墙阻挡。RoCE 还需确认 UDP 4791 开放。
UNREACHABLE 对端完全无法到达 先 ping 确认三层连通。ibping 确认 IB 链路 UP。 
# 验证 server 是否在监听（CM 默认端口 3891）
ss -tlnp | grep 3891
# 若没有输出，检查 Firewall
sudo iptables -L -n | grep 3891

数据传输异常

连接成功了，但是 ibv_poll_cq 返回了非 IBV_WC_SUCCESS 的完成状态。

WC 状态 含义 排查方向
IBV_WC_RNR_RETRY_EXC_ERR Receiver Not Ready——对端缓冲区未就绪 确认对端在发送前已 ibv_post_recv。检查 queue depth 是否匹配。增大 rnr_retry（最大值 7）。
IBV_WC_REM_ACCESS_ERR 远端访问权限错误 确认 MR 注册时包含 IBV_ACCESS_REMOTE_WRITE（RDMA WRITE）或 IBV_ACCESS_REMOTE_READ（RDMA READ）。检查 rkey 是否正确传递且未过期。
IBV_WC_REM_OP_ERR 远端操作不允许——操作码不匹配或无权限 对端 HCA 不支持该 WR 操作码（如 RC 上执行 UD 操作）。检查 QP 类型匹配。
IBV_WC_LOCAL_PROT_ERR 本地保护错误 SGE 中 lkey 无效、地址未注册、或 sge.length 超出 MR 范围。检查所有 SGE 参数。
IBV_WC_INV_REQ_ERR 无效的 WR 请求——参数错误 检查 ibv_send_wr 的 opcode、num_sge、sg_list。确保 wr_id 唯一。
IBV_WC_WORK_REQ_FLUSHED_ERR QP 已进入 Error 状态，所有在途 WR 被 flush 先确认前面的错误事件。将 QP 移回 Error 状态再重新建立（RC QP 在 Error 后不可恢复，必须销毁重建！）
关键提醒：RC QP 一旦进入 Error 状态——无论引起原因是什么——就不能重新初始化。必须 ibv_destroy_qp + ibv_create_qp 重建。这是设计约束，不是 bug。

资源泄漏

程序运行时出现 "cannot allocate memory" 或 "too many open files"。

# 查看当前资源的用量
rdma resource show qp
rdma resource show mr
rdma resource show cq
rdma resource show pd

# 确认进程的 memlock 限制（影响 MR 注册）
ulimit -l  # 应设为 unlimited 或足够大
现象 可能原因 修复
QP count 持续增长 连接/断开循环中未正确销毁 QP 确保每个 rdma_create_qp 有对应的 rdma_destroy_qp
MR count 持续增长 每次传输前注册新 MR，用完未注销 使用 registration cache 模式，预注册并复用 MR
PD count 增长 循环中创建 PD 未销毁 检查去初始化路径是否遗漏 ibv_dealloc_pd
fd 耗尽 Event channel 和 CQ 的文件描述符未关闭 每个 rdma_create_event_channel 和 ibv_create_cq 都需要对应的 destroy
内存泄漏 ibv_post_recv 分配的缓冲区未在清理时释放 使用 valgrind 定位泄漏。注意：valgrind 对 verbs 调用会产生大量 false positive，建议在 rdma-core debug build 下运行。
环境默认值：系统默认 max QP 约 16K，max MR 约 64K。生产环境应检查 /sys/class/infiniband/*/device/resource_* 并适当调大。在容器中通过 --ulimit memlock=unlimited 解决 MR 注册问题。

性能异常

功能正常但延迟偏高或带宽不达标。

检查项 最快验证 修复
CPU Affinity cat /proc/PID/status | grep Cpus_allowed_list 对网络相关的进程（主循环、轮询线程）执行 taskset -c N，N 应为 HCA 所在的 NUMA 节点上的核心。
中断分布 cat /proc/interrupts | grep mlx 确认中断被均衡到多个 CPU。使用 irqbalance 或手动 smp_affinity 调节。
Queue Depth perftest 中对比 -q 1 和 -q 64 的结果 增大预 posted 的 WR 数量，使 HCA 可以流水线化。
Signaled 策略 比较全部 signaled 和每 16 个 WR signaled 的性能 启用选择性 signaling：在 ibv_send_wr 中使用 IBV_SEND_SIGNALED 每隔 N 个 WR 请求一次完成通知。
Inline 检查 ibv_qp.cap.max_inline_data 对 ≤ max_inline_data 的消息设置 IBV_SEND_INLINE。减少 HCA 从内存中抓取小数据的 DMA 开销。
MTU ibv_devinfo | grep max_mtu vs 实际设置 ip link show 设置 path MTU 为硬件最大值。RoCE 网络 MTU 设 9000 减少报文头占比。
Soft-RoCE 结论 比较同一测试的 CPU 利用率 RXE 的带宽受 CPU 频率限制，不是网络问题。不要调优 Software 模拟器，调优你的 host CPU 调度。 
# 性能诊断参考命令
# CPU 亲和性检查
taskset -cp $(pgrep ib_write_bw)

# NUMA 拓扑（确认 HCA 所在的 NUMA 节点）
lstopo-no-graphics | grep -i infiniband

# 中断分布
cat /proc/interrupts | grep -E "CPU|mlx|rxe" | head -10

# MTU 确认
ip link show eth0 | grep mtu

# 测试不同 queue depth 的影响
ib_write_bw -a -d rxe0 -s 1048576 -q 1    # 单队列
ib_write_bw -a -d rxe0 -s 1048576 -q 128  # 深度队列
不要浪费时间：在 Soft-RoCE（RXE）或 TCG 虚拟化环境中，不要试图优化 "带宽达不到 100 Gbps" 或 "延迟大于 10 μs"——这是软件模拟的物理天花板。这些环境只适合功能验证。硬件性能基准必须使用真实 HCA。
