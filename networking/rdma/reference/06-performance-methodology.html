RDMA 性能测量方法论

延迟、带宽、queue depth、signaled 策略与 Soft-RoCE/TCG 的可信边界

测量对象

RDMA 性能测量不能只看 "延迟" 或 "带宽" 单一指标。不同应用关注的维度截然不同：

指标 典型范围 测量方法 应用关注
Latency（延迟） 1-10 μs（硬件）；10-100 μs（Soft-RoCE） Ping-pong（收发各一次，取半往返）；或者 WRITE_WITH_IMM 单边测量 高频交易、分布式锁、日志提交
Bandwidth（带宽） 12-200 Gbps（取决于硬件链路） RDMA WRITE 或 RDMA READ 大消息（≥1 MB）持续吞吐 存储（NVMe-oF）、数据备份、批处理
IOPS（消息速率） 1M-100M msg/s 短消息（64 字节）持续发送，统计完成数量 键值存储、消息队列、RPC 框架
CPU 利用率 <10% 典型硬件；50-100% Soft-RoCE perf stat 统计 cycles/byte、IPC、context-switches 云环境、功耗敏感场景
Tail Latency（尾部延迟） p99 < 3x 平均；p99.9 < 10x 平均 大量重复测试，排序取百分位数 SLA 保障、延迟敏感服务

关键参数

RDMA 基准测试的各个参数相互耦合，理解其影响对正确解读结果至关重要：

参数 扫描范围 影响
Message Size（消息大小） 64 B → 1 MB+（按 2x 递增） 小消息（< 256 B）测试消息率；大消息（> 64 KB）测试带宽。InfiniBand MTU 典型 4 KB，超过 MTU 需分段。
Queue Depth（队列深度） 1, 4, 16, 64, 128 深度 1 测量原始延迟；深度增大允许 HCA 流水线化，提升带宽利用率。过深可能导致 RNR 重试。
Signaled vs Unsignaled 全部 signaled / 选择性 signaled 每个 signaled WR 产生 CQE，消耗 CQ 带宽。选择性 signaled（每 N 个 WR 发送一个 signaled）可大幅降低 CQ 压力。
Inline 启用/禁用 小消息（≤ 发送队列的 max_inline_data）直接嵌入 WQE，避免 HCA 从内存 DMA 读取，降低延迟和内存带宽消耗。
CPU Affinity taskset -c N / isolcpus 将进程绑定到 HCA 所在的 NUMA 节点，避免跨 NUMA 访问引入额外延迟。isolcpus 隔离 CPU，避免调度抖动。

工具矩阵

perftest 是 rdma-core 自带的官方基准测试套件，覆盖主流操作：

命令 测量内容 典型用法
ib_send_lat 双向 SEND 延迟（ping-pong 半往返） ib_send_lat -a -d rxe0 -s 64 -n 10000
ib_write_bw RDMA WRITE 带宽 ib_write_bw -a -d rxe0 --report_gbits -q 64
ib_read_bw RDMA READ 带宽 ib_read_bw -a -d rxe0 --report_gbits -q 64
ib_send_bw SEND 消息率 ib_send_bw -a -d rxe0 -s 16 -q 128

重要参数说明：

  • -s size：消息大小（字节），必须服务端和客户端一致。
  • -n iterations：迭代次数，影响统计稳定性。建议 ≥ 10000。
  • -q depth：预 posted 的 WR 数量（queue depth）。
  • --report_gbits：以 Gbps 显示带宽，非默认 MB/s。
  • -a：自动判断设备，避免手动指定 GID。

辅助工具：

  • perf stat ./ib_write_bw ...：采集 cycles, instructions, IPC, cache-misses, context-switches。
  • rdma statistic：查看 per-QP 的发送/接收字节数、错误计数。
  • tcpdump -i eth0 udp port 4791：捕获 RoCEv2 流量，验证报文大小和重传。

实验设计

一份可信的 RDMA 性能报告必须遵循严格的实验规范：

  1. Warmup：前 N 次迭代丢弃（一般 ≥ 3 次）。RDMA 路径有初次运行时缓存未命中（TLB、页表缓存）和代码路径预热的冷启动效应。
  2. Repetitions：每个数据点至少 5 次独立运行，报告均值 ± 标准差。单次运行不可信。
  3. Randomization：如果需要扫描 size 序列，随机打乱扫描顺序，避免系统性的缓存或调度倾斜。或者使用双循环（先随机扫描再顺序确认）。
  4. Steady State vs Transient：测量持续 10 秒以上的稳态吞吐。系统在刚启动时有瞬时高延迟（调度器、中断合并调整）。瞬态测量结果不应混入稳态报告。
  5. 背景噪声控制：关闭 cron、日志轮转、监控 agent、NTP 同步等周期性任务。在隔离的 CPU 上运行（isolcpus 内核参数）。
# 评估用实验脚本片段（bash）：
for size in 64 128 256 512 1024 2048 4096 8192 16384 32768 65536 131072; do
    for run in $(seq 1 5); do
        ib_write_bw -a -d rxe0 -s $size -q 64 -n 10000 2>/dev/null \
            | tail -1 >> bw_size${size}_run${run}.dat
        sleep 1   # 让 HCA 和系统回归稳态
    done
done

Soft-RoCE/TCG 局限

重要警告：Soft-RoCE（RXE）和 TCG（QEMU 内部的虚拟 RDMA）的数值绝对不能用来推断或推测真实硬件 RDMA 的性能。以下列出其根本差异——每一个都导致测量值偏离硬件几个数量级。
方面 硬件 RDMA Soft-RoCE / TCG
数据路径 HCA 硬件 DMA，数据不经过 CPU CPU 执行 memcpy() 模拟 DMA。每个字节都由 CPU 搬运一遍。
延迟 1-3 μs（单跳） 20-200 μs（受 CPU 频率、内核抢占影响）。TCG 中每增加一层虚拟化增加 50-100 μs。
带宽 12-200 Gbps（线速） 受限于主机内存带宽的 1-5 Gbps（甚至更低，因单线程 memcpy 模型）。TCG 中因额外指令翻译进一步折半。
Queue Depth 效果 增大 QD 显著提升吞吐 QD 增大不显著提升吞吐，因为所有操作在 CPU 上串行化。
CPU 利用率 < 5% CPU 用于数据面 100% 单核满载（RXE 的 ksoftirqd 或 TCG 的 QEMU I/O 线程）。
尾延迟 稳定可控 高方差：受调度器、中断、宿主机负载大幅影响。

报告规范

一份可复现的性能报告必须包含完整的环境信息：

## 系统信息
- OS: Ubuntu 22.04.3 LTS (kernel 6.2.0-26-generic)
- rdma-core: v48.0 (git: v48.0-4-g1234abcd)
- CPU: Intel Xeon Gold 6338 @ 2.0 GHz (28C/56T)
- Memory: 512 GB DDR4-3200 (8 channels)
- NIC: Mellanox ConnectX-6 Dx (dual-port 100 Gbps)
- Firmware: 28.38.2002 (MT_0000000812)
- MTU: 4096 (IB link) / 9000 (RoCE eth)

## 测试配置
- QP Type: RC
- Access Flags: LOCAL_WRITE | REMOTE_WRITE
- Inline: enabled (max_inline_data = 64)
- Selective Signaling: every 16 WRs
- CPU Affinity: taskset -c 8-15 (NUMA node 0, same as NIC)
- Background: isolcpus=8-15, no cron/system services
- Iterations: 10000 (after 1000 warmup)
- Repeats: 5 per data point

不同测量目的的区别：

  • Functional Verification（功能验证）：确认代码无错误、路径通。用默认参数跑即可，不追求统计显著。
  • Micro-benchmark（微基准）：在最优配置下测得硬件上限。使用大页、绑核、隔离 CPU、优化参数。
  • Production Load（生产负载）：在接近生产环境的配置下测量——有背景噪声、非最优参数、真实消息分布。结果才是对业务有意义的参考值。

永远不要将 Soft-RoCE 或 TCG 的性能数据外推到硬件 RDMA。如果在软件模拟器上跑了 1 μs 延迟 100 Gbps 带宽，那测试环境或测试方法一定有问题。
