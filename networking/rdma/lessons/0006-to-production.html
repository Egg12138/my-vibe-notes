第六课 · 从 raw verbs 走向生产

理解 RDMA 生产生态：libfabric、UCX、MPI、NCCL，以及你已学到的知识如何复用

生产 RDMA 栈全景

在实际生产环境中，很少有应用直接调用 ibv_post_send 和 ibv_poll_cq。RDMA 软件栈是一个分层的金字塔：

MPI / NCCL / SHMEM | | UCX | | | libfabric | / \ | rdma-core EFA \ / \ \ \ InfiniBand RoCE AWS EFA ... (mlx5) (mlx5) (efa) 更抽象 / 更易用 ↑ | 每层都在复用下面的概念 | (MR, CQ, QP, WC, ...) | 更底层 / 更高性能控制 raw verbs ←──── 本课程 6 课的核心

为什么不用 raw verbs 写生产代码？

1. Provider 锁定

直接使用 ibv_* 函数族意味着你的代码被绑定到 InfiniBand Verbs API。如果你的应用需要同时支持 InfiniBand、RoCEv2、AWS EFA、Intel iWARP，用 raw verbs 需要为每个 provider 编写不同的后端。

相比之下，libfabric 通过 fi_getinfo() + provider 抽象层，让同一份代码可以不加修改地在不同 fabric 上运行。

2. 连接管理重复劳动

第五课展示了手工 TCP + raw verbs 的复杂度。生产中的连接管理还要处理：断线重连、多路径、多路复用（多个通信流共享一个 QP）、负载均衡。每个应用都重新实现这些逻辑是不现实的。

3. 错误恢复

RDMA 的 QP 一旦进入 ERR 状态，整个 QP 都不可用。生产代码需要检测错误状态、flush 待处理 WR、销毁旧 QP、创建新 QP、重新建立连接。raw verbs 把所有这些都留给应用处理。

4. 性能调优

不同的 RDMA 硬件有不同的性能参数：最优 inline 大小、doorbell 批量策略、CQ 轮询 vs 中断模式、NUMA 亲和性等。抽象层内置了常见硬件的调优经验。

libfabric：provider 抽象层

libfabric（也称 OFI Libfabric）是目前最广泛使用的 RDMA 抽象层。它为上层应用（如 UCX、MPI）提供了一组统一的 fabric API。

核心对象映射

libfabric 对象verbs 对应说明
fi_fabric()—（设备组）代表一组 RDMA 设备，范围最广的对象
fi_domain()ibv_pd资源隔离边界，对应 PD
fi_ep()ibv_qp通信端点，支持 RDM（可靠数据报）和 MSG（面向连接）两种类型
fi_mr()ibv_mr内存注册，与 MR 完全对应，也有 lkey/rkey
fi_cq()ibv_cq完成队列，与 CQ 完全对应

libfabric 的一大优势是 provider 切换：只需设置环境变量 FI_PROVIDER=tcp 就可以让 RDMA 代码回退到 TCP 模式，方便开发和调试。在生产环境中设置为对应的硬件 provider。

# 使用 TCP provider（开发环境）
$ export FI_PROVIDER=tcp
$ ./my_rdma_app

# 使用 EFA provider（AWS）
$ export FI_PROVIDER=efa
$ ./my_rdma_app

# 使用 Verbs provider（Mellanox RDMA）
$ export FI_PROVIDER=verbs;ofi_rxm
$ ./my_rdma_app

UCX：自调优的传输层

UCX（Unified Communication X）在 libfabric 之上提供更高层次的抽象。它的核心特点是 自调优传输选择：

  • 同一节点内通信 → 使用共享内存（shared memory）传输
  • 短消息（小于阈值） → 使用 RC QP SEND/RECV
  • 大消息 → 使用 RDMA WRITE 或 RDMA READ
  • 控制消息 → 使用 UD（不可靠数据报）

UCX 自动调节这些参数，应用不需要关心底层使用哪种传输机制。UCX 的 ucx_perftest 工具是衡量 RDMA 性能的行业标准。

高层框架：MPI 与 NCCL

在 AI 训练和 HPC 领域，最终用户通常不直接接触 libfabric 或 UCX。

  • MPI（Message Passing Interface）— 科学计算的标准并行编程模型。MPI 实现（如 OpenMPI、MPICH）内部使用 UCX 或 libfabric 作为传输后端。
  • NCCL（NVIDIA Collective Communication Library）— AI 训练中的集合通信库。NCCL 内部直接使用 libfabric 或 raw verbs（根据平台选择）。AllReduce、AllGather 等集合操作通过 RDMA WRITE 实现。

你在本课程中学到的知识如何复用

虽然生产代码不直接写 raw verbs，但你在前五课打下的基础在 RDMA 栈的每一层都适用：

你的知识基础生产环境中如何复用

生产中的真实挑战

用真实 RDMA 硬件运行生产负载时，你还会遇到 Soft-RoCE 环境中不存在的问题：

  • PCIe 带宽规划 — 多张 HCA 共享 PCIe root complex 时可能出现带宽争抢。需要配合 NUMA 拓扑仔细规划
  • 无损网络配置 — RoCEv2 需要 PFC（优先级流控）和 ECN（显式拥塞通知）来避免丢包。配置错误会导致 RDMA 性能急剧下降
  • 多路（Multi-rail） — 大型集群中每个节点有多个 HCA，需要负载均衡和故障转移
  • rkey 安全管理 — MR 的 rkey 相当于远程内存访问的密码。生产中对 rkey 的分发、旋转和回收需要严格管理
  • 资源隔离 — Linux cgroup rdma controller 可以限制每个 cgroup 的 MR 注册量、QP 数量等，防止一个应用耗尽所有 RDMA 资源
  • 可观测性 — 硬件计数器：CRC 错误、重传率、RNR 超时次数、PCIe 链路错误。ethtool、ibstat、perftest 等工具的使用
