## 这段要学什么

这段要解决的问题是：**一个补丁即使能通过 `kpatch-build`，为什么仍然可能不安全，或者需要重写。**

这是从“工具使用者”走向“补丁审阅者”的关键一步。

## 一句话理解补丁安全性

`kpatch` 只负责把补丁装进内核，不负责替你证明这个补丁对所有运行时状态都安全。

## 最核心的原则

作者指南里最重要的一句话可以概括成：

**不要盲目相信构建成功。补丁必须由理解目标代码和运行环境的内核专家逐个分析。**

这句话不是保守口号，而是 live patch 的现实约束：

- 运行中的任务已经持有旧状态
- 一部分线程可能处在旧函数路径里
- 另一部分线程会走新函数路径
- 新旧语义必须同时成立一段时间

## 数据结构变化怎么处理

指南里明确说了：**kpatch patch 函数，不 patch 数据。**

所以如果原始补丁要改结构体布局、数组布局、字段含义，通常不能直接照搬。

常见解决方法有两类：

1. **改使用代码，不改数据本身**
   - 把原本的数据修改，变成在使用点做分支判断
   - 这样更容易保持新旧对象共存时的安全性

2. **用 shadow variable**
   - 给旧对象外挂新状态
   - 避免直接改原结构体

这就是为什么 patch author guide 会反复强调“换思路，而不是直接改数据结构”。

## 数据语义变化怎么处理

有些补丁不是改字段，而是改字段的语义，比如：

- 计数器的含义变了
- 锁保护范围变了
- 某个状态位的解释变了

这类补丁看起来很小，但风险很高，因为：

- 老对象仍然按旧语义活着
- 新对象会按新语义创建
- patch 期间两种语义可能共存

所以作者指南建议：

- 用 shadow variable 区分“旧对象”与“新对象”
- 用条件分支同时支持新旧语义

## callbacks 为什么重要

`KPATCH_PRE_PATCH_CALLBACK`、`KPATCH_POST_PATCH_CALLBACK`、`KPATCH_PRE_UNPATCH_CALLBACK`、`KPATCH_POST_UNPATCH_CALLBACK` 这些宏的意义是：**把补丁生命周期里的额外状态处理显式化。**

它们适合做的事情包括：

- 预先准备资源
- 切换期间更新全局状态
- 卸载时恢复状态
- 做补丁前后的同步和收尾

你可以把它们理解成 livepatch 生命周期钩子。

一个实用判断标准是：

- 如果补丁需要“进入时改一次、退出时还原一次”，callbacks 往往比在普通函数里硬塞逻辑更清晰

## shadow vars 为什么重要

shadow variable 是 kpatch 处理结构体变化时最常用的逃生路径之一。

它解决的问题是：

- 不能改原 struct 布局
- 但新代码又需要附加状态

于是可以把新状态挂到对象上，按对象 ID 查找，必要时在老对象、新对象间同时运行。

这也是为什么补丁里常见这种思路：

- 创建新对象时分配 shadow
- 读取旧对象时先判断 shadow 是否存在
- 在 unpatch 或对象销毁时释放 shadow

## 进阶限制：jump labels 与 static calls

指南里的后半部分还会谈到一些更细的内核机制，比如：

- jump labels
- static calls
- system calls
- symbol versioning

这些主题的共同点是：**它们都不是普通函数调用路径。**

这意味着：

- 不能简单假设 `kpatch-build` 会自动把它们安全地翻译成可 livepatch 的形式
- 需要结合具体源码和目标内核版本判断

## 初学者版判断法

如果你看一个补丁，可以先问自己这 4 个问题：

1. 它只是改函数逻辑，还是改数据布局？
2. 它是否改变了运行时对象的语义？
3. 它是否需要 patch 前后做额外动作？
4. 它是否影响到特殊机制，比如静态调用、jump label、系统调用？

如果第 1 或第 2 个问题答案是“是”，通常就要提高警惕。

## 专家版判断法

更专业一点的判断顺序是：

1. 先确认是否存在“旧对象 / 新对象共存”问题
2. 再确认 patch 期间有没有跨版本状态迁移
3. 再确认是否需要 callback 或 shadow 变量维持一致性
4. 最后才看 `kpatch-build` 能否通过

这也是为什么作者指南和源码必须一起看：

- 指南告诉你“什么是危险的”
- 源码告诉你“这些危险是怎么被实现层面约束住的”

## 下一步怎么练

下一步最有效的练法是拿一个真实 integration case 来做四步分析：

1. 它改了什么
2. 它为什么不能直接改数据
3. 它是否用了 callbacks 或 shadow vars
4. 它最后在 build-time 和 runtime 各生成了什么

如果你继续，我建议下一段直接进入 `test/integration/`，拿一个具体例子从 patch 到模块到加载过程走一遍。
