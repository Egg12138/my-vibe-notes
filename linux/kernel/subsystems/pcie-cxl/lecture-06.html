实验 06: 驱动匹配与绑定

Part 1 · PCI Express 基础 · 枚举与绑定的解耦

原理

两条独立的路径

Linux PCI 子系统中，枚举和驱动绑定是两个完全分离的阶段：

  1. 枚举：PCI 核心扫描总线，发现 Vendor ID ≠ 0xFFFF 时创建 struct pci_dev。这个对象的存在由总线扫描和设备可达性决定。
  2. 驱动绑定：驱动注册时，PCI 核心将驱动的 id_table 与每个未绑定设备比较。匹配成功 → 调用驱动的 probe() → 建立绑定。
枚举（硬件驱动） 绑定（软件驱动） ──────────────── ──────────────── Bus scan driver_register() │ │ ▼ ▼ pci_dev 创建 match id_table │ │ ▼ ▼ sysfs 目录 probe() 成功 │ │ ▼ ▼ /sys/bus/pci/ driver 符号链接 devices/0000:01:00.0/ DRIVER= in uevent │ │ │ ▼ └──────────── 等待驱动 ──────→ bind

Match Key: modalias

每个 PCI 设备的 modalias 文件包含完整的匹配键：

pci:v00001AF4d00001044sv00001AF4sd00001100bc00scFFi00

每个字段：v=vendor, d=device, sv=subsystem vendor, sd=subsystem device, bc=base class, sc=sub class。驱动可以按 vendor/device、子系统 ID 或 class 等字段声明可接受的 function；modalias 把这些属性编码成可供模块自动加载和驱动核心匹配的字符串。

sysfs 绑定接口

每个 PCI 驱动的 sysfs 目录下有 bind 和 unbind 文件，允许用户空间手动控制绑定状态：

/sys/bus/pci/drivers/virtio-pci/
├── bind      ← 写入 BDF 来绑定设备
├── unbind    ← 写入 BDF 来解绑设备
└── 0000:01:00.0 → 当前绑定的设备符号链接

实验指导

目标

通过 sysfs 的 unbind/bind 操作，证明 PCI 设备目录在解绑后仍然存在，而 driver 符号链接和 uevent 中的 DRIVER= 行会消失和恢复。

操作步骤

  1. 运行自动观察： 
    make verify-06
  2. 交互式探索： 
    make run-06
    在 guest shell 中： 
    # 查看初始状态
cat /sys/bus/pci/devices/0000:01:00.0/modalias
readlink /sys/bus/pci/devices/0000:01:00.0/driver
grep DRIVER= /sys/bus/pci/devices/0000:01:00.0/uevent

# 解绑
echo "0000:01:00.0" > /sys/bus/pci/drivers/virtio-pci/unbind

# 观察解绑后的状态
ls /sys/bus/pci/devices/0000:01:00.0/driver   # 应该不存在
grep DRIVER= /sys/bus/pci/devices/0000:01:00.0/uevent  # 应该没有

# 重新绑定
echo "0000:01:00.0" > /sys/bus/pci/drivers/virtio-pci/bind

预期观察

  • 解绑后：设备目录仍然存在（证明设备由枚举维护，不是由驱动维护）
  • 解绑后：driver 符号链接消失，uevent 中 DRIVER= 行消失
  • 重新绑定后：driver 符号链接和 DRIVER= 行均恢复

解释

PCI 设备是总线资源，由 PCI 核心管理其生命周期。驱动是可选的消费者。设备不需要驱动也能存在于 sysfs 中并暴露完整的配置空间。这种解耦在热插拔和虚拟化场景中非常关键——可以安全地解绑旧驱动、绑定新驱动，而不影响设备在总线上的存在。

实验后恢复：在 make verify 模式下，init 脚本会自动执行 unbind → bind 并验证恢复。如果你在交互式 shell 中解绑了 virtio-rng，记得重新绑定，否则下一个实验（MSI-X）将看不到 IRQ。
