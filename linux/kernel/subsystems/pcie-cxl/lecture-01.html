实验 01: WSL2 vs QEMU 环境对比

Part 1 · PCI Express 基础 · 建立虚拟化环境认知

原理

虚拟化 PCI 总线

Guest 看到的是虚拟 PCI 视图：lspci 列出的是当前 Linux 所获准访问的 PCI function 及其配置空间，不是对宿主机插槽、Lane 或板卡的直接盘点。先划清这条边界，后续的 BDF、BAR 和驱动观察才不会被误读为物理拓扑测量。

当你在运行 Linux 时，lspci 列出的设备从哪里来？答案取决于你运行 Linux 的环境：

  • 物理机：固件初始化平台，并通过 ACPI 等机制向操作系统描述 PCI 根总线和资源；Linux 再扫描这些总线
  • WSL2：微软虚拟化层合成了一套虚拟 PCI 设备，不暴露宿主机 Windows 的物理 PCIe 拓扑
  • QEMU：QEMU 模拟了完整的 q35 芯片组，设备列表完全由 QEMU 命令行决定，可重现、可控
关键认知：虚拟化环境中的 PCI 设备是由虚拟化层合成的，不是直通硬件。理解这一点是后续所有实验的基础。

QEMU q35 机器模型

QEMU 的 q35 机器类型提供 Intel Q35 风格的 PCI 平台。即使本项目的命令行不添加教学设备，机器模型仍会提供启动所需的基础 PCI function；本讲关心的是这个本项目配置下的基线，而不是所有 q35 命令行都保证相同设备表。

BDFClass描述
00:00.00600Host Bridge（主桥）
00:1f.00601ISA Bridge（ISA 桥）
00:1f.20106SATA Controller（SATA 控制器）
00:1f.30c05SMBus Controller（SMBus 控制器）

在同一份 QEMU 命令行下，这些 function 会出现在相同的 BDF 地址上。这种确定性是教学环境的核心优势。

可控的模型，不是物理链路测量

QEMU 让我们精确控制 guest 可枚举的设备和拓扑，却不会复现宿主机的插槽布线、信号质量或真实链路训练时间。后续讲义使用 QEMU 来观察配置空间、层级和 Linux 资源模型；涉及 Lane 宽度、速率或热插拔电气行为时，应把它们视为独立的硬件问题。

实验指导

目标

对比 WSL2 和 QEMU 环境中 lspci 的输出，理解虚拟化 PCI 环境的基本特征。

操作步骤

  1. 记录宿主机（WSL2）的 PCI 设备： 
    make host
    输出保存在 build/host-lspci.txt。
  2. 启动 QEMU guest 并自动观察： 
    make verify
    输出保存在 build/qemu-serial.log。
  3. 比较两个文件中的设备列表——BDF 地址、vendor:device ID 和 class 都不同。
  4. （可选）交互式探索： 
    make run
    在 guest shell 中运行 lspci -nn 和 ls /sys/bus/pci/devices/。

预期观察

WSL2 的 lspci 输出包含 Hyper-V 为 guest 呈现的设备。QEMU guest 的输出显示本项目 q35 基线中的基础 function。两者都不是宿主机真实物理 PCIe 拓扑的直接记录。

解释

guest 仍会按普通 PCI 规则读取它看得见的配置空间并完成枚举；不同的是，虚拟化层决定哪些根总线和 function 对 guest 可见。QEMU 因而适合创建可控的、可重现的 PCIe 拓扑用于教学。

提示：如果卡住了，思考这个问题：QEMU 和 WSL2 哪一个让你能精确控制 PCI 设备的数量和类型？为什么这对学习很重要？
